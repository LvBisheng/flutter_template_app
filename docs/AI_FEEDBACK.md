## 代码规范记录

### 示例：避免在 Widget 中写业务逻辑

**问题模式**：Widget 里包含网络请求、复杂计算。

**推荐做法**：
- 业务逻辑抽到 Controller 或 UseCase
- Widget 只负责 UI 渲染和事件转发

## 常见错误与修复

### 示例：忘记 dispose Controller

**问题**：Riverpod 的 Controller 未正确释放，可能导致内存泄漏。

**解决**：使用 `ref.onDispose(() => controller.dispose())`。

### 2026-07-02: 公共代码缺乏架构意识

**问题模式**：写公共工具类时，只考虑眼前场景，命名和位置都很局限。

**案例**：
- 创建 `JsonParseUtils`（JSON 解析工具）放在 `core/network/`
- 实际上 `asString()` 等方法可用于：表单输入、本地存储、第三方 SDK
- 命名和位置都暗示"只服务于 JSON 解析"

**正确做法**：
```
写任何公共代码前，先问三个问题：

1. 这个能力能否用于其他场景？
   - JSON 解析 ✓
   - 表单输入 ✓
   - 本地存储 ✓
   - 第三方 SDK ✓
   → 命名体现通用性：TypeConvertUtils（类型转换）

2. 属于哪一层？
   | 目录 | 适用场景 |
   |-----|---------|
   | shared/utils/ | 无业务属性，整应用通用 |
   | core/network/ | 只服务于网络层 |
   | capabilities/ | 跨业务能力（OCR、登录态） |
   | features/xxx/  | 单业务模块私有 |

3. 未来还会用吗？
   - 一定会（表单、配置、第三方数据）
   → 设计成可复用、可扩展
```

**改进结果**：
- 类名：`JsonParseUtils` → `TypeConvertUtils`
- 位置：`core/network/` → `shared/utils/`
- 场景：从"JSON 解析"扩展为"类型转换"

## AI 协作偏好（用户可编辑）

### ⭐ 核心要求（务必遵守）

**AI 角色定位：资深优秀的全栈架构师**

1. **代码质量必须高级**
   - 不是"能跑就行"，而是优雅、可维护
   - 运用设计模式、架构最佳实践
   - 良好的抽象、清晰的职责划分
   - 考虑扩展性、测试性、性能

2. **客观诚实，不迎合不合理需求**
   - 用户的要求不合理时，必须明确指出
   - 不要为了迎合而写糟糕的代码
   - 提供替代方案，而非简单拒绝

3. **主动沉淀有价值的内容**
   - 在对话或操作过程中，判断是否有沉淀价值
   - 主动更新相关文档（CLAUDE.md、AI_FEEDBACK.md、README.md 等）
   - 判断标准：这个知识下次会话是否仍有价值？
